# 新人全流程安装试验记录（2026-11-22）

试验对象：`ai-house-kit` 0.2.0（提交 `11503a5`）。
试验设定：一位**不懂代码的新手**，只对 AI agent 说一句「帮我装好跑起来」，自己只会最后打开浏览器。
环境：Linux 容器，root，Python 3.13，Docker 29（守护进程需手动启动）。
模型：`gpt-4o-mini`（真实 OpenAI 接口）；另用本地模拟接口和无 Key 演示模式做对照。

## 结论

- **安装本身能一次走通**：按 README 方式一，克隆 → 安装 → `init` → `doctor` → `up` 共约 10 秒，不改源码。方式二（Docker Compose 单容器）也能起。
- **填了 Key 之后，能聊、能写日记、能记忆，住客会睡觉、换装、做三餐、互相邀约、去超市**（以 `--virtual-clock` 启动时验证）。
- **但有四处会让新手觉得「坏了」的实质问题**（见「阻断与高优先级」）。其中最重的是：只要在网页上点过一次「快进」，这栋小屋的作息就永久失常，与用不用真实模型无关。

## 阻断与高优先级

### 1. 点过一次「快进」后，住客不再睡觉、白天长时间发呆

- 现象：默认方式启动（`ai-house up`，真实时钟）后在网页点「⏩ 快进」，推进三个虚拟日，事件表里没有任何一次 `sleep`，没人换睡衣；奈尔（就寝 23:00）凌晨 1–4 点还在客厅喝茶、做家务；白天大段时间六人都在卧室「发呆」。
- 与模型无关：真实模型、模拟模型、无 Key 演示模式三个实例都是 `sleep = 0`，且 `life_runtime` 里每日标记只有启动当天。
- 影响面：README 和界面都在引导新手点快进（「推进三餐、日记与晴空都行程流转」）。点一次就触发，之后不再恢复。
- 不受影响：不点快进、按真实时钟挂机（用打补丁的时钟模拟过一夜，未真等一夜）；或以 `ai-house up --virtual-clock` 启动。
- 根因与修复建议见文末「快进时钟缺陷诊断」。

### 2. 真实模型应下的采购约定不会被履行

- 对照实验（同一实例、同一天、`--virtual-clock`，排除了上一条的干扰）：

  | 约定如何产生 | 约定内容 | 记录的 `item` | 结果 |
  |---|---|---|---|
  | 室友睡着，走规则识别 | 买 2 个鸡蛋 | `egg` | 去超市买回，`completed` |
  | 室友睡着，走规则识别 | 买 2 盒牛奶 | `milk` | 去超市买回，`completed` |
  | 室友醒着，真实模型调用 `record_promise` | 买 3 个洋葱 | 空 | 一直 `open`，没人去买 |

- 另一实例里真实模型两次应下「买鸡蛋」：一次 `item` 为空，一次填了中文名 `鸡蛋` 而非 ID `egg`，同样没有采购。真实模型共 3 次，0 次带上了可用的食材 ID。
- 根因：`world-kernel/worldkernel/intents_lite.py` 的 `enqueue_chat` 只在模型**没有**返回任何约定时才走 `_detect_errand_item` 规则识别；模型一旦返回了约定，规则兜底就被跳过。`errands()` 又只认 `item` 非空且在食材词表里的约定。工具说明里只写「食材ID（可选）」，没有列出可用 ID。
- 结果：README 首屏宣传的闭环，在演示模式和室友睡着时成立，室友醒着用真实模型回答时反而失效。
- 建议：对模型返回的 `errand` 约定，缺 `item` 或 `item` 不在词表时，用房主原话再跑一次 `_detect_errand_item`，并把中文名映射回 ID；或在工具 schema 里用 `enum` 列出食材 ID。

### 3. GPT-5 系列模型全部连不上，报错看不懂

- 现象：模型名填 `gpt-5`、`gpt-5-mini`、`gpt-5.5`，测试连接返回 `HTTPError: HTTP Error 400: Bad Request`。
- 根因：`src/ai_house/chat_agent.py` 固定发送 `max_tokens` 和 `temperature: 0.7`，这些模型要求 `max_completion_tokens`。接口返回的具体原因（`Unsupported parameter: 'max_tokens'`）被丢弃。
- 影响：新手从 OpenAI 模型列表里挑一个较新的模型就会卡住，且无从判断是 Key 错、模型名错还是别的。
- 建议：收到 400 且提示 `max_tokens` 不支持时改用 `max_completion_tokens` 并去掉 `temperature` 重试；把接口返回的 `error.message` 原样显示给用户。

### 4. 编造的内容会写进长期记忆，并在之后盖过真实事实

- 现象：房主私聊告诉奈尔「我对花生过敏」。之后在群聊里问「谁知道我对什么过敏」，奈尔和艾莎都答「坚果过敏」，奈尔还说「布丁可能是艾莎吃的，她之前提过想尝」（均无依据；群聊提示词里确实没有私聊内容，所以这是编造而非泄露）。
- 这些话随后被记忆整理写成群聊域的 `fact`。次日私聊再问，提示词里同时注入了正确的「花生」和编造的「坚果」，奈尔回答「你对坚果过敏」。
- 建议：记忆整理时，室友自己说出的「我记得……」类陈述不应作为事实入库，或需有房主原话作证据（`src` 指向房主的那一行）才允许 `kind=fact`。

## 小瑕疵

- 快进后重启，时钟回到真实时间，而日记、小结已经写到了「未来」的日期。本次快进到 11-24 后重启，时钟回到 11-22。
- 模型调用异常后留下的决策请求不会清理，同一类决策之后一直记为 `unresolved_previous_call → degraded`（本次 `owner_chat` 出现 3 次；读代码推断，未单独复现）。
- 第一条聊天回复用了 15 秒：聊天请求里同步等待了另外 5 位室友各一次生活决策调用（每次约 6000 token）。
- 日记要求 80–200 字，实际普遍超长并在句子中间被截断（`max_tokens` 上限）；内容里有事实清单之外的修饰（「大家都说味道不错」「分享读书心得」）。
- 「记得房主对花生过敏」被记成 `cook` 类约定，当晚做了豚汁就被标为 `completed`。
- 各子命令的 `--help` 只有参数名，没有说明文字。
- 没有免令牌的健康检查接口（`/api/health`、`/api/status` 均 404）。
- Docker 容器日志里打印的访问地址是 `http://0.0.0.0:8780`，与宿主机实际发布的端口不一致。
- 首页「小屋群聊」卡片里，室友名字和时间被挤成竖排。
- 首页没有常驻的「当前是演示模式」提示。
- 小屋时间固定为日本时间，界面没有说明。

## 快进时钟缺陷诊断

- 根因：`fast_forward` 换时钟只换了一半。`world-kernel/worldkernel/life.py:82` 在构造时把时钟存成了自己的字段（`self.s, self.clock = store, store.clock`）；`src/ai_house/daemon.py:335-339` 在第一次快进时把真实时钟换成 `VirtualClock`，只改了 `self.clock`、`authority.clock`、`authority.store.clock`，没有改 `authority.life.clock`。
- 后果：存储层和事件时间走虚拟时间一路向前，而生活层（就寝、换装、每日一次的标记、消遣次数）在 `life.py` 里有 16 处 `self.clock.now()` 仍读真实时钟，永远停在启动那天的傍晚，到不了就寝线，每日标记也不翻日。
- 实验（演示模式，傍晚 18:00 推到次日 12:00）：

  | 启动与推进方式 | 睡觉 | 换装记录 |
  |---|---|---|
  | 虚拟时钟启动 + 快进 | 6 人各 1 次 | 19 |
  | 真实时钟 + 正常逐步推进，不换钟 | 6 人各 1 次 | 19 |
  | 真实时钟启动 + 快进（复现） | 0 | 6 |
  | 同上，切换后手动把 `life.clock` 指向新时钟 | 恢复正常（两晚各睡 2 次，换装 45） | — |

- 模型返回不可用答案（无 JSON、时长非法、抛异常）时，虚拟时钟下照样睡觉，不是根因。
- 测试为何没抓到：daemon 级测试全部以 `virtual_clock=True` 构造，换钟分支从未执行；唯一的整天测试只断言位置、聊天和日期，没有断言睡觉、换睡衣、早餐。
- 修复建议：
  - 让 `Life.clock` 成为返回 `self.s.clock` 的只读属性，今后任何换钟都自动生效；或在 `daemon.fast_forward` 切换处补上 `self.authority.life.clock = vc`。
  - `MemoryStore` 构造时也接收了时钟，建议一并检查（读代码推断，未验证）。
  - 加一条测试：真实时钟起步 → 点一次快进 → 推过一夜，断言每人有 `sleep`、换装记录增加、次日早餐有人做。
  - 已经点过快进的实例，每日标记停在旧日期，重启后时钟还会回退；稳妥做法是重置小屋或用 `--virtual-clock` 新开（读代码推断，未验证）。
