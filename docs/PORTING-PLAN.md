# 功能移植方案

日期：2026-11-22　状态：**已批准，待执行**（维护者的四项决定见第 6 节，执行须知见第 7 节）；**第 14 节是 2026-11-24 的方案修订稿（纯逻辑模块由“搬行为”改为“搬代码”），待维护者确认。** 第 12 节“住客大脑改接 agent”：维护者 2026-11-23 定了方向（12.6），主引擎当天实现并用真外壳加模拟模型端验证（12.7），2026-11-24 经中转用真的 Claude 模型跑了两轮（`LONGRUN-2026-11-23.md` 第 6 节）

本文回答一个问题：维护者自用的私有部署（下称“私有端”）里已经有很多能力，怎样把它们变成新人装完 kit 就能用、且适合开源的可配置功能。

本文只写能力和做法，不含私有端的路径、账号、人设和基础设施细节。

## 1. 结论

1. **内核已经对齐，差距在内核之外。** kit 的 `worldkernel` 包与私有端几乎逐模块一致。私有端多出来的是内核外的一层：通道桥（工具、主动发言、发送护栏、模型链路）、记忆的证据与泄露防护、完整的约定系统。
2. **kit 现在的插件机制承接不了“可配置的开源插件”。** 必须先补底座，再搬功能。
3. **搬行为，不搬代码。** 私有端的通道桥是约 8 千行的单文件，绑定了另一套 agent SDK 和本机环境；kit 是标准库单进程。以私有端的测试为规格，在 kit 里重写。
   **（2026-11-24 修订稿：这一条收窄为只适用于通道桥；记忆、约定这类纯逻辑模块改为搬代码。理由和做法见第 14 节。）**
4. **QQ 协议端不重做。** 现成的 OneBot 端可以与 kit 并排运行，kit 只负责把自己的 OneBot 插件做可靠。
5. **长期把方向反过来**：kit 当上游，私有端变成“kit + 私有覆盖层”。否则每次移植都是一次性的，两边会继续分叉。
   **（2026-11-24：分叉已经量出来了，见 14.1。）**

### 2.3 不移植

| 项 | 原因 |
|---|---|
| 真实账号的空间动态、收藏表情同步 | 依赖真实账号 |
| 需要登录凭据或成人内容的抓图功能、搜书发书 | 内容与合规风险 |
| 私人云盘画廊、模拟器手机与电视 | 私人资产 |
| 本地 LoRA 与专属声线 | 私人资产；只保留“自带引擎”接口 |
| 协作与巡检 agent、API 中转代理 | 私人运维 |
| 私有表情包素材 | 版权 |
| 内核之外的旧世界控制器 | 私有端自己也处于向内核过渡的阶段；kit 直接以内核为准 |
| 私有端的大控制台 | 强依赖容器编排；只借鉴思路（日记书架、记忆分页、用量页） |

### 2.4 共同依赖

私有端的记忆、约定、世界、通道桥都依赖同一个身份层，它只按 QQ 号认人。这一层不先在 kit 里抽象出来，上面几项都搬不动。

## 3. 原则

1. **一个能力一个插件。** 插件自带清单：配置字段、类型、默认值、是否密钥、依赖什么。
2. **默认关闭，未配置时安静降级。** 不报错，不影响其他功能。沿用现有演示模式的思路。
3. **网页里能配完。** 控制台按清单自动生成表单，密钥只回显掩码。
4. **核心保持标准库。** 需要第三方包的能力走可选依赖，和现在的 `[onebot]` 一样。
5. **收敛配置面。** 每个插件对外的字段尽量不超过 8 个，其余用内置默认值。
6. **测试用合成数据。** 从私有端移植测试时，只移植断言和场景，数据重新造。
7. **脱敏闸门。** CI 在现有密钥扫描之外，再查绝对路径、邮箱、疑似账号的长数字。私有标识符的黑名单放在仓库外，由本地推送前的检查使用。

身份层的要求（已决定与渠道解耦）：

- 记忆、约定、发送门只认内部身份，不直接读渠道账号。
- 网页端和 OneBot 端的同一个人要落到同一个身份上。

### 7.3 规则

- 一个阶段内的每一项单独开 PR，标题写明对应的编号（例如“1.4 模型层抽象”）。
- 提交前跑全部测试。基线随合入增长，以 `main` 上最近一次 CI 为准。
- CI 的 `test` 三个版本全部通过之后才能合并。PR #32–#36 都是在 CI 跑完之前合并的，合并后测试是红的，`main` 因此红了约一个半小时，到 #37 才恢复。
- 修复类 PR 的每一条都要有“修复前失败、修复后通过”的测试，并且要覆盖变体和反例，不能只测声称成立的那一条路径。
- 核心不加第三方依赖；需要的话走可选依赖，并先开 issue 讨论（见 `CONTRIBUTING.md`）。
- 测试只用合成数据和假模型，不联网。
- 不提交任何密钥、账号、真实聊天记录，以及私有端的路径、人设和基础设施细节。
- 从私有端参考行为时，只带走行为和测试场景，不复制代码。
- 完成一项后更新下面的进度表，并把测试结果写进对应的 PR 说明。
- 实施中发现方案与实际不符（尤其是第 5 节的未核实项），先改本文再改代码。

### 8.3 已知遗留

以下是验收和复核里复现过或读代码确认、这一轮没有修的，大致按影响从大到小：

- **回执前断线的回复仍会丢**。发送后、协议端回执前连接断开时，这条回复不重发（重发可能重复）。崩溃恢复时个别气泡可能重发一次。
- **没有主语的采购句不建约定**。“下班带杯奶茶”“明天买点菜”这类句子分不清是让室友买还是房主自己买，规则不处理，交给模型的意图抽取；没配模型时就漏掉。“酱油用完了，麻烦买一瓶”这种要回指上一句的也不处理。
- **同一张图会下载两次**：看图在回复前下载一次，相册归档在回复后再下载一次。两者都有超时，只是多花一次流量。
- **宿主句柄不是沙箱**。第三方插件与宿主同进程，公开接口已不越权，但经对象内部仍摸得到真对象；注册一个通道就能读私聊范围。文档已写明，装第三方插件等同于信任它的代码。
- **`daemon.py` 里仍按插件 id 写死了几处**（群行为、主动发言、相册、OneBot），没有全部改成钩子。
- **运行锁的边角**：同一进程里起第二个守护进程会直接接管锁；持锁进程死掉后它的 pid 若被别的进程复用，按代码会被当成仍在运行而拒绝启动（未实际复现；删掉 `.daemon.lock` 即可）。
- **通道状态里的“被限流”信息**（`OneBotChannel.status_view()`）还没有接到任何 HTTP 接口或页面上，目前只在日志里看得到。
- **熔断用的是小屋的时钟**。用 `--virtual-clock` 且时钟冻结时，熔断打开后要等快进才恢复。
- **总时限管不住慢速滴灌**：单次网络读取的超时是逐次计的，一个每隔几秒吐一个字节的端点可以超过总时限。
- **相册上限按条数算**（每个频道 200 张聊天图），没有按字节算。
- **没有做的验证**：真实模型的 32 小时长跑、真实 systemd 上的常驻。真实 QQ 与真实协议端在 4.4 做了第一次，范围很窄，见第 9 节。

## 11. 两条设计结论（2026-11-23）

复测留下两条“是不是有意的设计”的问题，维护者定了第一条，第二条对照私有端后确认不用改。

### 11.1 时间归内核管

**结论**：小屋的时间只由内核推进，内核之外的任何东西都不能干涉。这也是私有端的做法：那边没有任何从外部补步或快进的接口，虚拟时钟只出现在测试和影子运行里。

kit 之前的做法与此不符：`POST /api/step` 对写档令牌开放，网页上有“+1 步”“+15 分钟”“+60 分钟”，在按真实时钟运行的小屋上点一次，小屋时间就永久跑到真实时间前面。

改动：

- 按真实时钟运行（默认的 `ai-house up`）时，`POST /api/step` 对任何令牌都返回 409，网页不再显示推进按钮。
- 用 `--virtual-clock` 启动的演示小屋本来就没有别的时间来源，仍可手动推进，但只认房主令牌，写档令牌不行。
- 状态接口多一个 `manual_time_control` 字段，页面据此决定显示什么。
- 房主的化身、补货、出门这些动作不受影响：它们只是把请求交给内核，由内核在当前时刻处理，不改时间。

没有动的：以前在真实时钟小屋上点过快进留下的时间偏移（`clock_offset.json`）仍然生效，小屋时间会继续比真实时间快那么多。要回到真实时间，只能重置小屋或删掉这个文件后重启（后者未验证事件记录里“来自未来”的条目会怎样，不建议在有数据的小屋上做）。

测试：`world-kernel/test_tail_12_kernel_owns_time.py`（9 条）。两种小屋各起过一栋，在浏览器里确认过管家页和首页。改动后的全量结果（本地干净检出，Python 3.13）：

| 提交 | world-kernel | world-catalog | world-contract-tests |
|---|---|---|---|
| `92e7ada` | 1063 通过 | 22 通过 | 11 通过 |

### 11.2 同一句话，两位室友各应一条约定

**结论**：这是既定设计，私有端也是这样，不改。

- 私有端：约定按“谁答应的”记。房主在群里说一句，两位室友各自答应，就各有一条“她答应房主”的约定；只有参与者完全相同的才会合并成一条（两位室友约好一起做的事，各自整理出来的是同一条）。完成只认凭据，涉及房主的约定世界不能替人判完成。
- kit：同一句话应下的几条约定共用一个计划编号，参与者合并，其中任何一位办成，几条一起结单。复测里看到的“两条都结单、只有一次采购”就是这个机制。另做了三次模拟（两位室友同应“买两盒牛奶”，各推进两天），每次都只有一位去买，没有重复采购。

两边的差别在完成方式：私有端每条要各自的凭据，kit 是一人办成全体结单。对采购这类事，kit 的做法不会让第二个人白跑一趟，所以保留。

没有验证的：真实模型下两位室友是否总会都去调用记约定的工具；以及界面上两条约定并排显示会不会让人误以为要买两次（目前没有标出它们是同一件事）。

## 12. 住客大脑改接 agent（2026-11-23；方向已定，见 12.6）

### 12.1 为什么

维护者的判断：住客后面接 agent 比 kit 自己写调用循环更好，有些能力可以直接拿来用。私有端就是这样做的，kit 当初按“搬行为，不搬代码”改成了直连 OpenAI 兼容接口（第 1 节第 3 条）。这一节把那条决定改掉一半：**聊天这条线可以换成 agent，直连保留为零依赖的默认和回退。**

现在两边的差别：

| | 私有端 | kit 现状 |
|---|---|---|
| 住客怎么说话 | agent 自己调用“发消息”“保持安静”等工具，说不说、说几条、先查什么都由它定 | 程序选好谁回，模型返回一段文字，程序切气泡 |
| 工具 | 进程内挂二十多个工具，另挂一个共享服务；单轮最多 12 步 | 自己写的循环：最多 3 轮、每轮 4 个调用；内置 3 个工具加插件工具 |
| 会话 | 长会话，存编号，下次接着同一段上下文；上下文自动压缩 | 每次重新拼提示词，带最近 6 条历史 |
| 现成能力 | 联网搜索与抓取、一个只属于自己的记事本目录 | 没有（联网搜索是另写的插件） |
| 管控 | 每次工具调用过一道策略回调和钩子 | 回复出来之后过发送护栏和泄露检查 |

三路只读调查的要点（2026-11-23）：

- **Agent SDK**（以官方文档为准）：pip 包自带运行时，不用另装 Node；Python 3.10 起可用。一个会话对应一个子进程，官方建议每个按 1 GiB 内存起步估算，实际占用和启动延迟文档没有给数字。自定义系统提示、进程内工具、关掉全部内置工具、多轮续接、自动压缩、自动提示词缓存都有。接口是异步的，同步多线程服务怎么接，官方没有现成做法。
- **官方只支持 Claude 系模型**（API 密钥、Bedrock、Vertex）。可以把地址指到中转，但中转必须说 Anthropic 的协议，文档明说不支持经中转接非 Claude 模型。**不允许**第三方产品让使用者用 Claude 订阅登录。
- **kit 的接缝**：带工具的循环只有一处（`chat_agent.py` 的 `_run_tool_loop`）；现有插件扩展点里没有一个能替换“调用模型 + 工具循环”这一步；`/mcp` 端点是给外部客户端以房主身份连进来用的，不能替住客说话。生活决策、记忆抽取、日记都是“一次调用、返回 JSON 或一段文字”，与 agent 的多步循环不是一回事。

### 12.2 做法

**在 `chat_agent` 里抽出一个“大脑”接口，现有循环是它的一种实现，agent 是另一种。** 接口以外的东西都不动：身份判定、提示词里的人设与屋内状态、回复后的护栏与泄露检查、约定入库、记忆、发送门。

不选另外三种接法的原因：

- 接在模型路由下面：路由的语义是“一次补全”，agent 自带多步循环，硬塞进去等于只用它一步。
- 做成第三方插件：现有扩展点接不住，要新开一个扩展轴，而且第三方拿不到做这件事需要的句柄。等接口稳定后再开放成扩展点。
- 让 agent 在外面经 `/mcp` 反向连进来：账本、时限、熔断全部失效，还要在同步的对话流程里加一套请求等待机制。

分四步，每步一个 PR，前一步验收过再做下一步：

| 步 | 内容 | 规模 |
|---|---|---|
| A0 | 抽接口。现有循环原样搬成“直连大脑”，行为不变，现有测试不改 | 小 |
| A1 | “agent 大脑”：可选依赖 `ai-house-kit[agent]`；每位住客每个对话一个长会话，会话编号存盘；工具仍是 kit 现有那几个（内置 3 个加插件工具），由 agent 自己决定怎么用；**最终回复仍是一段文字**，所以后面的护栏、约定、记忆一概照旧 | 中 |
| A2 | 放开现成能力，按小屋配置逐项开关，默认全关：联网搜索与抓取；每位住客一个只属于自己的记事本目录。每次工具调用过策略回调 | 小到中 |
| A3 | 住客自己决定怎么说话：“发消息”（可以多条）“保持安静”做成工具，群聊里由 agent 决定接不接话。这一步改的是行为，要和发送门、群聊规则重新对接 | 中到大 |

A1 里必须自己补上的东西（否则换了大脑就少了保护）：

- **记账**：把每轮的用量写进现有的用量账本，用量页照常能看。
- **时限**：对话的总时限管不到子进程，要用超时加中断自己实现。
- **熔断与回退**：agent 连续失败时停一会儿；配了直连的回退到直连，没配的退到演示回复并说明原因。
- **报错说明**：SDK 的错误类型接进现有的中文说明。
- **隔离**：不读本机任何 Claude 配置，配置目录放在小屋的数据目录里，关掉自动记忆。
- **资源**：闲置的会话关掉子进程，再说话时按会话编号续接。
- **线程**：一个专用线程跑事件循环，其他线程把任务提交给它。

不改的：生活决策、记忆抽取、日记、主动发言、看图这些单次调用继续直连。它们要的是便宜、稳定地返回一段 JSON，agent 帮不上忙；私有端的记忆抽取也是单次调用。

### 12.3 需要维护者定的四件事

| # | 问题 | 建议 |
|---|---|---|
| 1 | agent 大脑支持哪些模型 | 官方支持的三种接法（API 密钥、Bedrock、Vertex）作为正式支持；另外允许使用者自己把地址指到一个说 Anthropic 协议的中转，文档写明这是自担风险的用法。**kit 不自带协议转换中转**（与第 2.2 节“不移植中转代理”一致） |
| 2 | 默认用哪个大脑 | 默认仍是直连，agent 要装可选依赖并显式打开。等 A1 在真实模型下跑过一昼夜，再议是否把默认换过来。README 里“零依赖”的说法保持成立 |
| 3 | 能否一栋小屋里混用 | 可以，按住客配置（和现有的“按住客选模型”一个思路），成本不高 |
| 4 | 做到哪一步 | 先做 A0、A1 并实测；A2、A3 看 A1 的结果再定 |

第 1 件事有一个眼前的后果：这次长跑用的是 OpenAI 和 Gemini 的密钥，**它们驱动不了 agent 大脑**。A1 的验证需要一把 Anthropic 的密钥，或者一个说 Anthropic 协议的中转地址和它的凭据。

### 12.4 风险和没查清的

- **内存与延迟**：6 位住客同时活跃就是 6 个子进程。每个占多少内存、冷启动多久、一句简单问答比直连多花多少 token，文档都没有数字，要在 A1 验收时实测并写进文档。
- **条款**：使用 SDK 受 Anthropic 的商业条款约束；产品命名不能用 “Claude Code”；不能提供订阅登录。SDK 仓库页面标的是 MIT，许可证正文还没读，加依赖前要核对。
- **隔离不是完全的**：关掉配置来源之后，SDK 仍可能读到本机的全局配置和托管策略，所以要给它单独的配置目录，并在容器里验证。
- **测试**：CI 里没有密钥，agent 大脑只能对着一个按 SDK 接口写的假客户端测，真实行为靠手动长跑。这正是前几轮吃过亏的地方（第 10 节的两点提醒），A1 的验收必须包含真实模型的一昼夜。
- **同步与异步的桥**：官方没有指导，线程里跑事件循环是我们自己的做法，要专门测并发和取消。
- **Windows 与非 glibc 镜像**：ARM64 Windows 没有自带运行时；Alpine 之类是否可用文档没说。先只承诺 Linux（glibc）和 macOS。

### 12.5 和阶段 5 的关系

阶段 5 是“kit 当上游，私有端变成 kit 加覆盖层”。私有端的通道桥有两部分：一部分是 agent 外壳（会话、工具、策略），一部分是只属于私有端的工具和人设。A0–A3 做完后，前一部分在 kit 里，后一部分正好就是覆盖层：以 kit 插件工具的形式挂上去。所以这一节实际上是阶段 5 的前置。

### 12.6 维护者的决定（2026-11-23）与据此调整的做法

**决定**：

1. **用现成的 agent，不另写一套。** 私有端这套做法已经证明可用、够结实，kit 照它来。
2. **引擎**：私有端当初试过三个 agent 外壳（Claude Code、Codex、Antigravity），当时 Claude Code 表现最好，所以它是主引擎。**另外两个预留接口**。用 Gemini 的人，建议走 Antigravity（下称 agy）搭建。

这回答了 12.3 的第 1 件事，也改了 12.2 的两处：

- 12.2 里 A1 写的是“最终回复仍是一段文字”，A3 才让住客自己调用工具说话。**现在合并**：从一开始就按私有端的方式，住客用“发消息”工具说话、用“保持安静”工具不说话。这是那套做法里被验证过的部分，不拆开。
- 12.3 第 1 件事原来建议“只正式支持 Claude 系模型，其余靠使用者自己的中转”。**现在改为按引擎分**：Claude 系模型走 Claude Code 引擎；OpenAI 的走 Codex 引擎（预留）；Gemini 的走 agy 引擎（预留）。kit 仍然不自带协议转换中转。

12.3 的第 2、3、4 件事维护者没有另外表态，先按原建议做：默认仍是直连（不装可选依赖也能启动），按住客可以混用，先做完主引擎并实测。

**引擎接口**照私有端已有的切口来。那边换引擎时只换三样：建会话、丢会话、跑一轮；工具统一经一个工具服务暴露（Claude Code 引擎挂在进程内，agy 引擎连本机回环地址上的同一个服务，带每个会话各自的令牌）。kit 的接口就是这三样加一个工具服务，Codex 和 agy 两个名字先占位，选到它们时给出明确的“尚未实现”和接口说明。

**从私有端照搬的行为**（这些是“够结实”的来源，逐条都要有测试）：

| 行为 | 作用 |
|---|---|
| 每个对话一把锁，全局限制同时跑的轮数；活跃会话有上限，闲置 30 分钟的会话关掉子进程 | 控制内存和并发 |
| 会话编号存盘，下次续接；外壳明说会话找不到才立刻开新会话，其他起不来的情况（连接失败、进程没出声就退出）保留编号、连续记数，连续两轮之后第三轮才换新会话 | 重启后不断片，一次网络抖动不清掉长会话，坏会话也不会永远卡死 |
| 住客只写了文字、没调用“发消息”：当轮提醒一次；仍没发，下一轮开头再提醒；连续三轮都这样就换新会话 | 模型学坏了能自己拉回来 |
| 私聊里提醒过仍只写文字的，把最后一段文字代发出去 | 私聊不至于没回音 |
| “发消息”的结果一回来就中断，不等模型再多说一句 | 省一次调用，回得快 |
| 结果里报告的耗时比本轮实际经过的时间还长，说明它是上一轮的迟到结果：跳过，最多三次，之后当作本轮的结果收下；外壳一直不出结果时，靠本轮总时限（默认 120 秒）到点丢掉这个进程，下一轮重新续接 | 避免每条回复都晚一轮 |
| 会话累计的上下文超过上限就换新会话，并带一张“接续条” | 控制每轮成本 |
| 新会话的第一轮先说明“换了新会话，需要时自己去翻最近的记录” | 不凭空编之前的事 |
| 每次工具调用先过策略回调，钩子里记数、留审计记录 | 工具可管可查 |
| 不读本机任何 Claude 配置，配置目录单放，关掉更新和遥测 | 隔离 |

**不搬的**：只属于私有端的工具和功能（空间、小游戏、翻唱、信箱、运维对话等）、人设、账号、基础设施。它们以后以 kit 插件工具的形式挂上去，这就是阶段 5 说的覆盖层。

**kit 这边接在哪**：聊天模块里“调用模型加工具循环”那一段换成“交给引擎跑一轮”。一轮里住客发出的几条消息合起来就是这一轮的回复，照旧经过护栏、泄露检查、约定入库、记忆和发送门；选择“保持安静”就是这一轮不回。现有的 3 个内置工具和插件工具原样进工具服务。

**验证需要的东西**：主引擎要一把 Anthropic 的密钥，或者一个说 Anthropic 协议的中转地址和凭据。OpenAI 和 Gemini 的密钥驱动不了它。在拿到之前，引擎只能对着按 SDK 接口写的假客户端测。

### 12.7 实现与验证（2026-11-23）

**做了什么**

- 新包 `src/ai_house/agent/`：`engine.py`（引擎接口：建会话、丢会话、跑一轮；工具统一经 `AgentSession.call_tool`）、`runtime.py`（会话与轮次，对所有引擎相同）、`claude_engine.py`（Claude Code 引擎）、`reserved.py`（Codex、agy 占位与接口说明）、`prompts.py`。
- 接入点：`chat_agent.py` 的 `reply_as`（选到 agent 时交给引擎跑一轮，失败时有直连就走直连、没有就明说）；`daemon.py`（运行时随小屋创建与关停、重置世界时清会话和外壳留下的对话文件、群聊里“不接话”不入库不外发、被护栏拦下时告知住客、对话总时限随 agent 时限放宽）。
- 设置：`AI_HOUSE_BRAIN`、`AI_HOUSE_ACTOR_BRAIN_<住客>`，默认 `direct`。可选依赖 `.[agent]`。使用说明在 `docs/AGENT-BRAIN.md`。

**小屋是多线程同步程序，SDK 是纯异步的**，两者这样接：运行时自己开一个事件循环线程；`run_turn` 在调用者线程上阻塞，等待期间住客的工具调用被送回调用者线程执行。这样小屋工具的运行位置（线程、时限、SQLite 用法）和直连方式完全一样。

**和 12.6 不同的两处**

| 12.6 写的 | 实际做的 | 原因 |
|---|---|---|
| “发消息”的结果一回来就中断 | 用外壳的 PostToolUse 钩子在工具返回时结束本轮；中断保留为后备 | 用真外壳实测：中断到达时外壳已经发起了下一次模型请求（一轮 2 次调用），钩子能赶在它之前（一轮 1 次） |
| 没有提默认模型 | 默认 `sonnet` 别名 | 实测不指定时外壳请求的是当时最大的型号，日常聊天偏贵 |

**没搬的**：私有端“带一张接续条”里如果有对话摘要，kit 没有做摘要，只带一句说明，靠 kit 自己的记忆系统补（`search_memory`）。上网和笔记本工具没有开放。

**真外壳验证**（`world-kernel/test_agent_3_real_shell.py`）：真的 Claude Code 外壳（`claude-agent-sdk` 0.2.172 自带的可执行文件）接本地模拟的模型端（`agent_mock_api.py`）。只有“模型说什么”是模拟的；外壳、策略回调、进程内工具服务、会话文件、重启续接都是真的。探针在清空环境变量的子进程里运行，接触不到任何真实凭据，也没有通往本机以外的路。实测结果：

- 9 轮：通过工具发消息、调用小屋工具后把结果说出来、一轮发两条、忘了发被提醒后补发、请求内置工具被外壳拒绝、群聊不接话、重启后续接并记得之前说过的暗号；再加一轮故意卡住的（模型端 12 秒才答，小屋 5 秒就不等了），以及紧接着的一轮——同一个会话接着用，还记得暗号，没有被上一轮拖住。
- 每次工具调用都经过了策略回调（逐次记录）；小屋工具在调用者线程上执行。
- 外壳向模型端提供的工具只有小屋的工具，没有读写文件、执行命令、上网这些内置工具。
- 外壳的文件都在小屋数据目录下；`~/.claude` 没有被创建。

**独立评审与修复**。实现完成后请了一轮不看作者结论的评审，查出并修掉的：

| 问题 | 怎么发现的 | 处理 |
|---|---|---|
| “发完即止”的测试在 Python 3.11 上必挂（假客户端靠让出次数赌调度顺序） | 评审在 3.11 上连跑 6 次都失败 | 假客户端改成确定性的：默认模拟钩子停下，另有开关模拟钩子没生效、明确等中断 |
| agent 这一轮失败、又没有直连模型时，气泡里写的是“配置错误：没有可用的接口”，真正的原因被盖掉 | 评审脚本 | 没有直连端点就直接说 agent 的原因；另补：全屋走 agent、某位住客却设成直连而直连没配，明说是配置错误 |
| 同一个对话两条消息紧挨着来，前一轮超时后，后一轮会接着用那个半死的外壳进程 | 评审脚本 | 超时的那一轮在还握着这个对话的锁时就把进程关掉 |
| 关掉一个还在干活的外壳要等它 5 秒，这 5 秒里占着锁，下一轮白等 | 给真外壳补“超时”一轮时测出来的 | 先发中断再断开，实测即时关闭 |
| 续接后第一轮只要没成功就判“会话没了”，一次网络抖动会清空整段长对话 | 评审脚本 | 只有外壳明确说会话不存在才立刻换新；别的失败先留着，连续两轮才换；新会话没跑通之前不把空编号存盘 |
| 重置世界只清了会话登记，外壳自己存的对话文件（含房主私聊）还在；不用 agent 的小屋重置时也会凭空多出一个文件 | 评审读代码 + 脚本 | 重置时删外壳的对话文件和工作目录；没有会话可存时不写文件；重置时正在连接的外壳连上后立即丢弃 |

### 13.4 记忆框架逐项对照

结论：**同一思路的两条分支，已经实质不同**。两边都是“观察 → 定期整理 → 召回 → 发送前检查”，都是 SQLite 加可选向量加字对关键词，容量和阈值的量级相同（每人 3000 条、每次召回 6 条 700 字、合并阈值 0.92、泄露判据的三个基本数）。但表结构、范围的叫法、可信度、召回带什么、泄露检查的口径都不一样，库不能直接互搬，名字相近的开关含义也不同。

| 项 | kit | 私有端 | 判断 |
|---|---|---|---|
| 范围 | 私聊 / 群 / 世界，按频道分 | 自己的 / 私密 / 公共，按会话分，另有把不同平台的群对成同一个群的别名表 | 不一致 |
| 统一记忆 | 默认关；开了只让群范围跨频道 | 按住客开，全员开着；自己的和公共的记忆在所有会话（含私聊）都可见 | 不一致 |
| 可信度 | 三级可信度；群里别人说的降为“未核实”；只凭住客自己说的话不入库；与已核实事实冲突的降权并标“勿采信” | 没有可信度；反而要求记下住客自己的承诺和给过的具体内容 | 不一致，且是产品取向不同 |
| 召回打分 | 向量 + 关键词 + 新近度 + 可信度系数 | 向量 + 关键词；没有新近度和可信度 | 不一致 |
| 召回时引用原话、旧版本 | 不引用（来源只用来判可信度） | 引用出处原话和“此前是……”的旧版本 | 私有端有，kit 没有 |
| 说话人的人物卡、房主立的规矩 | 没有单独处理 | 当前说话人的卡常带；房主私聊里立的规矩在所有会话单独成块 | 私有端有，kit 没有 |
| 还没整理的原话 | 只在开关一打开时取房主私聊里的陈述句 | 近 6 小时内来自别的群或房主私聊的行，相似才带 | 不一致 |
| 没找到时 | 明确提示“照实说不记得，别编”；含糊追问时给最近几条私聊 | 返回空，没有这句提示 | kit 有，私有端没有 |
| 住客自己存、搜、忘 | 只能搜 | 三样都有，公开保存前另有一道检查 | 私有端有，kit 没有 |
| 私聊记忆进群 | 开关一，独立 | 开着，且只在统一记忆打开时生效 | 依赖关系不同 |
| 不拦的群 | 开关二，默认空，写错拒绝启动 | 默认值写死为自家的屋群，没有校验 | 默认值不同 |
| 出站泄露判据 | 基本判据相同，另加“重合够多”“敏感短语”“过敏线索”三条，再加一道 12 字连续重合的检查 | 基本判据；是否另有连续重合检查没查 | kit 更严 |
| 检查不可用时 | 本地函数，没有“不可用”这条路 | 拒发；附件或转发拿不到可核对文字时也拒发；群友私聊、临时会话强制检查 | 私有端更严 |
| 不拦的群里豁免谁 | 只豁免这位住客自己听到的私聊 | 整个群对这位住客不查 | 不一致 |
| 过期 | 有到期时间和定期清扫 | 没有 | kit 有，私有端没有 |
| 遗忘 | 房主在控制台作废；清掉版本和来源 | 住客自己也能忘；清掉版本和来源 | 入口不同 |
| 日记 | 程序按当天记录生成，不读房主私聊；存在“世界”范围，私聊和群里都能召回；泄露检查不覆盖日记；没有“日记私密”开关 | 住客晚间自己写；有“日记私密”开关，代码默认私密，现在的取值是不私密，住客在群里想得起自己的日记 | 眼下效果接近，机制不同 |
| 结构迁移 | 有版本表 | 没有版本号，按需补列 | 不一致 |

试点前最该对齐的五件（建议，由维护者定）：

1. **日记**：kit 加“日记私密”开关并把日记纳入出站比对，再定试点用哪个值。
2. **两个开关的默认值和依赖**：保留 kit 的“默认空 + 写错拒绝启动”；“私聊进群要不要求统一记忆”两边说法要一致。
3. **泄露检查**：判据以 kit 为准，“不可用就拒发”和附件无法核对时拒发以私有端为准。
4. **可信度**：群聊里以 kit 为准（防止传言被记成事实）；但“记下住客自己的承诺”要不要保留，是产品决定。
5. **召回**：互补。kit 补“引用原话”和“房主规矩块”（来源表已有，只差召回时读）；私有端补“不记得就照实说”。

没查的：私有端世界范围的记忆、它的发送前检查里除泄露之外的各道门、两边日记配图、kit 的备份是否含记忆库。

### 13.5 试点建议

- 先选私有依赖最少的住客，最后才动依赖最重的那位。
- 同一个号两边同时接，协议端允许，但两边会各回一条，所以并行期 kit 一侧必须只听不发（需要 13.3 第一项）。2026-11-24 的真实群验证（`LONGRUN-2026-11-23.md` 第 9 节）是把原程序暂停几分钟来做的，不是并行。
- 切换按住客走：影子 → 放开一个低风险群 → 放开私聊。回滚就是停掉 kit 一侧、恢复原程序；两边记忆库分开，不用回滚数据。

### 13.6 需要维护者定的

1. 回复闸门和外部裁判：进 kit 的标准挂点，还是一直留在覆盖层？
2. 泄露检查不可用时拒发，要不要成为 kit 的默认？
3. 不拦的群的默认值以哪边为准？
4. 日记在群里能不能被召回？

## 14. 方案修订稿（2026-11-24，待维护者确认）

### 14.1 为什么要改：分叉量出来了

### 14.2 改哪几条

1. **纯逻辑模块搬代码，不重写。** 记忆、约定和内核一样，以私有端现行代码为底，去掉私有内容后进 kit。“搬行为，不搬代码”只留给通道桥（它确实绑着另一套环境）。
2. **测试跟着代码一起搬。** 私有端这两块的 187 个用例进 kit，作为一致性测试；以后 kit 在这两块上的任何改动都不能让它们变红。
3. **一份代码，kit 当上游。** 搬过来之后，这些模块只在 kit 里改；私有端改用 kit 的这一份，自己只留配置和适配（阶段 5 的方向，提前到这几个模块上先做）。私有端切过来之前，哪边改了都要同步到另一边。
4. **漂移要看得见。** 仓库里留一个对照脚本，在维护者的主机上跑，输出 14.1 那样的表；每次动这几个模块、每次发布前跑一次，数字记进文档。相同行的比例掉了就要说明原因。
5. **kit 独有的增强逐项定去留，不再以“kit 自己的实现”存在。** 三级可信度、“查不到就照实说不记得”、到期清理、开关写错拒绝启动：要么并进共同的那份代码（两边都得到），要么做成开关且默认值跟私有端一致，要么放弃。
6. **在对齐完成之前，kit 的记忆和约定只修缺陷，不加新行为。**

- **kit 现有用户的记忆库要迁移。** 表结构和范围的叫法都要变，迁移必须可回退。
- **kit 这两天在记忆和约定上修的东西可能要重做一遍。** 长跑查出的问题（闲聊被记成约定、过期约定的追问、编造）在私有端代码上是否同样存在，要用同一份剧本重跑才知道；存在的就修在共同的那份代码里。
